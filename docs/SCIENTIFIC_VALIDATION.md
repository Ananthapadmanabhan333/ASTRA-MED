# Scientific validation

How ASTRA-MED's AI models are evaluated, what has been shown and, as importantly, what has not.
Every number below is reproduced by a command in this repository; nothing is estimated, copied or
hand-edited.

> **Synthetic-data validation only.** All crew data are generated by the ASTRA-MED simulator. The
> results show how well each method recovers the simulator's injected events and dynamics. They do
> **not** establish clinical or real-world accuracy. No model has been validated on astronaut or
> patient data, and no output may be used as a diagnosis.

## 1. Validation tiers

| Tier | Question it answers | Status |
| --- | --- | --- |
| 0. Software verification | Does the code do what it specifies? | **Done.** 300+ backend tests (metrics, causal features, chronological splits, calibration, explanations, serving) |
| 1. Synthetic validation | Do the methods recover known, injected events and dynamics? | **Done.** Headline run plus a three-dataset replication study (this document) |
| 2. Retrospective validation on real research data | Do they work on real physiological recordings? | **Not done.** No public astronaut vital-sign time series exists without a data-use agreement (NASA LSDA crew data are restricted). Public clinical waveform databases could support an *analogue* study under their own terms; none was used |
| 3. Prospective analogue validation | Do they help in a realistic operational setting (analogue mission, isolation study)? | **Not done** |
| 4. Clinical validation | Are they safe and effective for crew medical decisions? | **Not done and not claimed.** ASTRA-MED is not a medical device |

The rest of this document is about tiers 0 and 1.

## 2. Evaluation framework

**Code:** `backend/app/ai/experiments/` (config, runner, report, tracking), `backend/app/ai/metrics.py`,
`backend/scripts/seed_study.py`. **Command:** `python -m app.ai.train` (full run, about 4–6 minutes on
a laptop CPU).

### Data and splits

- **Dataset:** 120 simulated days for four crew members at 5-minute resolution (138,240 windows,
  fingerprint `eabfda075aa4`, seed 7). It contains 327 injected events (255 sudden, 72 gradual, 148
  of them subtle), 3 % missing values and 112 artefact spikes that are **not** labelled anomalies.
- **Splits:** chronological and day-aligned. Train is the first 60 % (to 2026-03-17), validation the
  next 20 % (to 2026-04-10), test the last 20 % (to 2026-05-04).
- **Forecasting** splits the validation period again: the first half for early stopping, the second
  half for conformal calibration.

### Leakage prevention (each item is enforced in code and covered by a test)

| Rule | Where | Test |
| --- | --- | --- |
| Splits never overlap in time | `datasets/synthetic.chronological_split` | `test_chronological_split_has_no_overlap` |
| Features are causal (only past windows) | `features.build_features` | `test_features_are_causal_and_complete` |
| Personal baselines and scalers are fitted on clean training windows only | `pipeline.prepare` | runner design; `test_baseline_is_activity_and_time_of_day_aware` |
| Detector thresholds are set on validation normal windows, never on test | `runner.run_anomaly` | report states the rule; per-run results record it |
| Feature-set selection uses validation AUPRC; test columns are reported for ablation only | `runner.run_anomaly` | ablation table marks the selected set |
| Forecast targets never cross a split boundary | `forecasting/data.origins` | `forecasting.data` masks |
| The test split is scored once per run | `runner.run` | — |

### Metrics

| Task | Metrics | Notes |
| --- | --- | --- |
| Anomaly detection (window level) | Precision, recall, F1, AUROC, AUPRC, **false-positive rate** (FP / (FP + TN)), **false-negative rate** (FN / (FN + TP)), specificity | AUPRC matters more than AUROC at a 10–15 % anomaly rate (Saito and Rehmsmeier 2015) |
| Anomaly detection (event level) | Share of events detected, by type and intensity; median detection delay | An event counts as detected if any of its windows is flagged |
| Operational view | False warnings per crew-day and events warned when a warning needs 2 consecutive flagged windows | Closer to what a crew would experience |
| Forecasting | MAE, RMSE, **MAPE** where meaningful, empirical coverage of 90 % split-conformal intervals, skill vs personal climatology | MAPE only for ratio-scale signals (heart rate, SpO₂, respiratory rate). Body temperature in °C has an arbitrary zero, so a percentage error is meaningless and is not reported (Hyndman and Koehler 2006) |

### Models compared

- **Anomaly detection:**
  - A statistical personal-baseline detector.
  - Isolation Forest, Local Outlier Factor, One-Class SVM and an autoencoder.
  - A weighted ensemble of calibrated scores.
  - The phase 2 fixed-threshold alert rules, as a baseline.
- **Forecasting:**
  - Three baselines: persistence, seasonal naive, and personal climatology for the planned activity.
  - XGBoost with engineered features.
  - LSTM, GRU and TCN.

Every hyperparameter is recorded per run in `results.json` and in the report's
*Hyperparameters* table. They were fixed before the runs; the test split was never used to tune anything.

### Versions and experiment tracking

- **Model versions:** each training run is an immutable version `v<UTC time>-<config hash>`. Its
  manifest holds the config, dataset fingerprint, git commit, library versions and a SHA-256 for
  every file. Loading verifies the hashes before any pickle is opened. `ASTRA_AI_MODEL_VERSION` pins a
  version, which is also the rollback mechanism.
- **Experiment index:** [`backend/experiments/results/experiment-index.md`](../backend/experiments/results/experiment-index.md)
  lists every registered version with its headline metrics.
- **Full report of the serving version:**
  [`backend/experiments/results/latest-report.md`](../backend/experiments/results/latest-report.md).

## 3. Results

### 3.1 Reproducibility

The same configuration was trained twice, two days apart: `v20261112-164739-9c1cd54f` from commit
79f7060, and `v20261114-115210-9c1cd54f` from 8fae33c plus the phase 7 changes. **Every reported
metric was identical**, for all 7 anomaly models and all 7 forecasters, to the 4th decimal.

The phase 7 inference benchmark then exposed one real reproducibility bug at serving time.
`planned_steps` picked a tied dominant activity state with `max(set(...))`. Python's set order for
strings depends on a per-process hash seed, so neural forecasts for the same input differed between
processes by up to 7.8 bpm. Training results were not affected: training uses the observed steps,
whose tie-break is stable. The fix uses the earliest state, matching training. A regression test
runs the planner under four hash seeds, and the forecast is now bit-identical across processes.

### 3.4 What the evidence supports, and what it does not

1. **Every learned detector beats the fixed-threshold rules**, by a margin far larger than the
   run-to-run spread. F1 is 0.62–0.81 for the learned detectors against 0.36 for the rules; the
   false-negative rate is 0.27 against 0.77.
2. **The ensemble is not demonstrably better than LOF alone.** The headline run ranks the ensemble
   first, but across three datasets the ensemble (F1 0.800 ± 0.052) and LOF (0.811 ± 0.029) overlap
   completely. The ensemble is kept because it is never much worse than its best member and its
   explanations combine several views, not because it is more accurate.
3. **XGBoost is the best forecaster**, ahead of all neural models and the baselines in every run.
   The gap to the neural models is about 0.8 bpm at 1 h, several standard deviations. The neural
   models do not justify their cost on this data.
4. **Split-conformal intervals are close to nominal**: 0.89–0.91 against 0.90 in every run. The
   exchangeability assumption behind conformal prediction only holds approximately for time series,
   so coverage is measured, not assumed.
5. **The statistical detector has high AUROC but low F1.** It ranks windows well, but at the 1 %
   false-positive operating point it misses most windows of slow events.
6. None of this transfers automatically to real astronauts. The simulator, its events and the labels
   share one design (see section 5).

## 4. How to reproduce

```bash
cd backend
python -m app.ai.train                              # headline run; registers a new model version
python scripts/seed_study.py --seeds 7 11 23        # replication (~15 min; registers nothing)
python -m app.ai.experiments.tracking               # refresh the experiment index
python -m pytest tests/ai tests/phase7 -q           # evaluation, metric and serving tests
```

Runs with the same config hash and dataset fingerprint must reproduce the same metrics. If they do
not, compare the library versions recorded in each manifest first.

## 5. Limitations

- **Synthetic data only.** Events, physiology and labels come from one design, which makes detection
  easier than real monitoring, where events are unlabelled, heterogeneous and rare.
- **Labelled calibration.** Thresholds are calibrated on labelled validation data. A real deployment
  has no labels and would need clinician-reviewed calibration.
- **Plan equals reality.** Planned activity equals actual activity in the simulator, so the
  forecasters' strongest feature (the planned schedule) is unrealistically reliable.
- **Small replication.** Three replication runs give only a rough idea of variability, not a
  confidence interval.
- **No real-data validation** at tiers 2–4. That is the next scientific step, not a formality.
