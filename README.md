# ASTRA-MED

Astronaut health monitoring and predictive decision-support prototype for the
**NASA Space Apps Challenge 2026**. A mission-control dashboard watches a fictional four-person crew
in Mars transit: live vitals and a synthetic ECG, history, alerts, anomaly detection, radiation dose,
sleep and circadian drift, rule-generated insights, and an experimental AI intelligence center
(personal baselines, multivariate anomaly detection, 24-hour forecasts, early-warning scores, explanations),
a space environment intelligence center built on real NASA open data (DONKI space weather, ISS
cabin and radiation measurements from the OSDR Environmental Data App, OSDR study metadata), and
medical decision support: a digital health twin per crew member, six-system health intelligence,
explainable decision support for every significant alert, an emergency scenario simulator,
structured incident reports with PDF export, a source-grounded medical data assistant and a mission
health overview, behind sign-in with role-based access and an audit log. Phase 6 joins it all into
one mission control platform: a command dashboard, crew monitoring, one event history and alert
centre for every module, a situational-awareness timeline, an isolated mission simulation sandbox,
mission analytics and platform health checks.

> **All data is simulated.** Crew members are fictional, and every measurement is generated by the
> built-in physiological simulator and labelled `simulated`. ASTRA-MED is a research prototype. It is
> not a medical device and has not been clinically validated. Thresholds and insights are software
> test scenarios, not diagnoses. The AI models are trained and evaluated on simulated data only; their
> results say nothing about real-world or clinical accuracy.
>
> **The space environment pages use real NASA data**, each value labelled as measured, environmental
> indicator, model output, estimate, simulated or catalogue metadata. Historical ISS measurements are
> never shown as live telemetry. A solar event is never turned into a crew dose. Correlations are
> exploratory and do not establish causation. ASTRA-MED is not affiliated with or endorsed by NASA.

## NASA Space Apps Challenge 2026

**Challenge:** [Create Health Monitoring Software for Astronauts on Space Missions](https://www.spaceappschallenge.org/2026/challenges/health-monitoring-software/).

ASTRA-MED gives each astronaut a self-check (body-systems map, glucose, mood and symptom check-ins,
daily check prompts, when to involve the flight surgeon). It also learns each crew member's own
normal, flags unusual patterns, forecasts the next 24 hours
with honest uncertainty, explains every alert, and places it in its space-environment context using
real NASA DONKI and OSDR data. Results on simulated data, over three independent datasets:

| Measure | Learned methods | Baseline |
| --- | --- | --- |
| Anomaly detection F1 | 0.62–0.81 | 0.36 for fixed alarm limits |
| Heart-rate forecast error at 1 h | 2.2 bpm | 3.9 bpm for a personal baseline |
| Coverage of 90 % prediction intervals | 89–91 % | (nominal 90 %) |

There is no clinical validation ([details](docs/SCIENTIFIC_VALIDATION.md)).

### Use of AI in building ASTRA-MED

The source code, tests and documentation were written with the help of an AI coding assistant
(Anthropic's Claude, used through Claude Code), working from the team's specifications. Commits it
co-wrote carry a `Co-Authored-By: Claude` trailer. The application's own models (anomaly detectors
and forecasters) are conventional machine-learning models trained on the simulated data in this
repository. The optional Claude mode of the medical data assistant is off by default.

## What's inside

| | |
| --- | --- |
| **Simulator** | Python physiology model: heart rate, SpO₂, blood pressure, temperature, respiratory rate, synthetic ECG, sleep, exercise, radiation. Circadian and activity effects, correlated noise, deterministic seed |
| **Event engine** | Tachycardia-like, bradycardia-like, desaturation, elevated temperature, abnormal respiratory rate, irregular rhythm, solar particle event. Operator-triggered or random |
| **Detection** | Activity-aware threshold rules, ECG rhythm irregularity, personal-baseline z-score. Full alert lifecycle with acknowledge/resolve |
| **API** | FastAPI REST + WebSocket (`/ws/health-monitoring`), Pydantic contracts, PostgreSQL history, structured logs, uniform error envelope |
| **AI engine** | Personal baselines, statistical / Isolation Forest / LOF / One-Class SVM / autoencoder detectors with a calibrated ensemble, XGBoost / LSTM / GRU / TCN forecasts with conformal intervals, rule-based risk scoring, SHAP and occlusion explanations, versioned and hash-verified model registry |
| **Space environment** | DONKI flares, CMEs, SEP events, geomagnetic storms, radiation belt enhancements, notifications and WSA-ENLIL runs; ISS cabin temperature, humidity, CO₂ (14 missions) and dosimetry (11 missions) from 2014–2024; OSDR study catalogue. Resilient async ingestion (retries, failover, rate limits, caching, offline fallback), radiation intelligence in four separate categories, a UTC mission timeline with display timezones, and an exploratory correlation engine (Pearson, Spearman, lagged, rolling, autocorrelation-adjusted, FDR-controlled) |
| **Medical decision support** | Digital twin (daily summaries over the whole mission, stored vs regenerated days, baseline vs current, trends, stages), six-system assessment with cross-system patterns, eight-part decision packets with a process-only review workflow, emergency simulator (7 scenarios, severity, duration, AI analysis, timeline), incident reports (10 sections, SHA-256 integrity, review sign-off, PDF), cited assistant with a safety layer, mission health overview |
| **Security** | Sign-in with scrypt-hashed passwords, server-side sessions (HttpOnly cookie + CSRF token, or bearer tokens), lockout and rate limiting, four roles with a permission matrix, audit log, security headers |
| **Mission control** | Event orchestration (timestamp synchronisation, P1–P4 prioritisation, de-duplication, history) fed by monitoring, AI, NASA DONKI, the habitat, emergency runs and reports; unified alert centre with acknowledgement, required resolution notes, correlations and an audit trail (experimental AI capped at P3); mission simulation sandbox with its own clock (speed, pause, reset, presets, event injection, telemetry ingestion, AI analysis, reports, playback); analytics with CSV / JSON / Markdown export; component health and database consistency checks |
| **Dashboard** | Next.js 16, TypeScript, Tailwind CSS v4, shadcn/ui, Recharts. Collapsible sidebar, mission header, notification centre. Types generated from the API's OpenAPI document |

## Run it

### Option A: Docker Compose (PostgreSQL + API + dashboard)

```bash
cp .env.example .env        # then set POSTGRES_PASSWORD
docker compose up --build
```

Open http://localhost:3000 for the dashboard and http://localhost:8000/docs for the interactive API docs.
The first start applies the database migrations and trains the AI models into the `ai-artifacts`
volume (about 6 minutes on CPU) before the API comes up; later starts reuse them. Compose is a local
stack; for a public deployment follow [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md). (Docker could not be
run on the development machine, so the images and Compose file are reviewed but untested.)

### Option B: local development (no Docker; SQLite by default)

Backend (Python 3.11+):

```bash
cd backend
python -m venv .venv
.venv/Scripts/activate          # Windows; use `source .venv/bin/activate` on macOS/Linux
pip install -r requirements-dev.txt
uvicorn app.main:app --reload --port 8000
```

Frontend (Node 20+), in a second terminal:

```bash
cd frontend
npm install
npm run dev
```

The first backend start creates the schema and backfills 7 days of history (about a second).

Train the AI models once (about 6 minutes on CPU; writes a version to `backend/artifacts/`). Until then the
dashboard works and the AI pages say no model is available:

```bash
cd backend
.venv/Scripts/python -m app.ai.train       # add --quick for a 15-second smoke run
.venv/Scripts/python -m app.ai.demo        # optional: controlled scenarios -> experiments/results/demo.md
```

`requirements-dev.txt` installs CPU-only PyTorch from the PyTorch index. For a lighter install, use
`requirements.txt` alone: the autoencoder and the LSTM/GRU/TCN forecasters are skipped, and the other
models work.

To use an existing PostgreSQL server, set `ASTRA_DATABASE_URL=postgresql+asyncpg://user:password@localhost:5432/astra_med`
in `backend/.env` (see `backend/.env.example`).

### Option C: PostgreSQL without Docker

`pgserver` ships PostgreSQL 16 binaries as a Python package, so you get a real PostgreSQL server
with no Docker and no system install. From `backend/`, with the virtualenv active:

```bash
pip install -r requirements-pg.txt
python scripts/local_postgres.py serve
```

This starts PostgreSQL (data in `backend/.pgdata`), creates the `astra_med` and `astra_med_test`
databases, and runs the API against it. Then start the frontend as in option B. Other commands:
`start`, `url`, `status`, `stop`. The server listens on 127.0.0.1 only and uses passwordless local
auth, so treat it as a development database.

### Sign in

Every page except the sign-in screen needs an account. Create local demo accounts (one per role:
`surgeon`, `operator`, `analyst`, `admin`) against the database the API uses:

```bash
cd backend && .venv/Scripts/python scripts/create_users.py dev
```

The passwords are random and written to `backend/.dev-users.json` (git-ignored; delete it when you
are done). For real accounts use `scripts/create_users.py add <username> --role <role>`, which
prompts for the password. With Option C, prefix the command with
`ASTRA_DATABASE_URL=$(.venv/Scripts/python scripts/local_postgres.py url)`; with Docker, run it inside
the `api` container. Roles and permissions are in [docs/SECURITY.md](docs/SECURITY.md).

### Try the alert path

1. Open **Anomalies & tests**, choose *Oxygen desaturation* for Lukas Brandt, and select **Start test scenario**.
2. Go to **Mission control**. Within about 40 s SpO₂ falls below 94 %, a caution alert opens and escalates to
   critical, the crew row turns red and a notification appears.
3. Acknowledge and resolve it from **Alerts**, with an optional note.

The simulator also starts random scenarios (6 per hour by default, `ASTRA_RANDOM_EVENTS_PER_HOUR`).

For NASA data, open **Space weather** under *Space environment*.

- **First start:** the backend synchronises DONKI (last 180 days), the OSDR catalogue and the EDA
  missions in the background. Pages show "Waiting for first sync" until then, and keep working on
  stored data if NASA is unreachable.
- **Your own data:** **NASA data explorer** shows every source's provenance, licence, quality and
  sync log, with a "Synchronise now" button.
- **Report:** regenerate the data source documentation report with:

```bash
cd backend && .venv/Scripts/python -m app.space.report --out ../docs/reports/nasa-data-sources-report.md
```

For medical decision support, sign in as `operator` and open **Emergency simulator**:

1. Choose *Oxygen desaturation*, Lukas Brandt, *Severe*, then **Run simulation**.
2. After a minute, select **Run AI analysis**: the six systems, patterns, alerts and escalation are
   stored on the run.
3. In **Medical intelligence**, select the alert to see its eight-part decision packet, then
   **Create incident report**.
4. In **Incident reports**, **Submit for review**. Then sign in as `surgeon`, **Start review** and
   **Mark reviewed** with a note.
5. **Open PDF** exports the report.
6. Ask the **AI medical assistant** "Explain the latest alert for AST-02": every statement is cited
   and labelled.
7. Sign in as `admin` to see the audit trail of all of the above.

For the AI path, open **AI intelligence**. It shows each crew member's risk card and the crew-wide early-warning
queue, then a 24-hour forecast with its interval, the anomaly timeline and the personal baselines, each with
an explanation. **Explain** on any alert shows why it fired. **Model evaluation** shows the test-split metrics.

### Try mission control (phase 6)

Sign in as `operator`. **Mission control** is the command dashboard. Open **Mission simulation**,
choose *Medical emergency: oxygen desaturation* at 20x and **Start simulated mission**: the sandbox
runs on its own clock (amber marking), the scripted desaturation opens a `[SIM]` alert, **Send
measurements** pushes readings through the same detection, the AI panel analyses the stream, and
**Report** on an alert creates a sandbox incident report. Follow it in the **Alert centre**
(*Simulation sandbox*), **Situational awareness** (choose the run under *Data*) and the dashboard,
then replay it under **Mission playback**. The full demo script is in
[docs/PHASE6_REPORT.md](docs/PHASE6_REPORT.md#6-demo). The same eleven-step workflow runs against a
live API with `cd backend && .venv/Scripts/python scripts/e2e_mission.py`.

```bash

```

## Configuration

All backend settings are `ASTRA_*` environment variables (`backend/.env.example` lists them all). The frontend
reads only public values: `NEXT_PUBLIC_API_URL`, plus `NEXT_PUBLIC_WS_URL` if the WebSocket lives elsewhere.
No secrets are committed; Compose takes the database password from your `.env`.

A personal NASA API key (free, from https://api.nasa.gov/) is optional: set `ASTRA_NASA_API_KEY` in
`backend/.env` or the root `.env`. It is read only by the backend. It is never logged, stored,
returned by the API, or sent to the browser. Without it, NASA's public `DEMO_KEY` is used, and DONKI
falls back to the keyless CCMC web service. On 2026-11-12 the api.nasa.gov DONKI proxy was returning
HTTP 404 after DONKI's move to new CCMC URLs, so CCMC serves the data either way.

Authentication is on by default (`ASTRA_AUTH_ENABLED=true`). Behind HTTPS set
`ASTRA_AUTH_COOKIE_SECURE=true`, serve the dashboard and API from the same site, and list the
dashboard origin in `ASTRA_CORS_ORIGINS`. `ASTRA_AUTH_ENABLED=false` is for isolated development only
and is refused when `ASTRA_ENVIRONMENT=production`. The assistant runs offline by default;
`ASTRA_ASSISTANT_MODE=claude` (with `ANTHROPIC_API_KEY` and `pip install anthropic`) sends questions,
simulated records and documentation passages to the Anthropic API.
